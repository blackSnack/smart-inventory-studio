# Native dependent business completion (#23)

Photo creation: choose the real Part category, read direct templates and explicitly accept/omit every nonblank recognized field and deduplicated source link. Only compatible reviewed scalar bindings and source-backed parameter values may be queued. Missing/unsupported mappings or evidence must be fixed in the reviewed form or deliberately omitted, not silently dropped. The queue binds each dependent enrichment to the exact verified Part creation acknowledgement, IPN and category. It rechecks template mapping before preparation and before write. Each operation has its own approval and readback. Source links are attachments, not file downloads or manufacturer/supplier identity creation.

Cabinet migration: load managed cabinet metadata and choose a drawer; split one compartment by equal integer proportions or merge contiguous selected compartments. Bind every resulting compartment to an existing eligible leaf or request a new leaf. Read the actual stock rows, explicitly allocate each moved StockItem and exact decimal quantities. All stock in removed leaves must move; mixed targets, unsupported lifecycle, incomplete child lineage, serialized partial splits and quantity conflicts stop preparation. The native operation queue creates new leaves first, resolves IDs only from correlated verified acknowledgements, then moves stock. Repeated splits of the same originally ordinary root StockItem are supported only with verified prior moves and matching child/remainder evidence. Prior child destinations are re-read; unknown outcomes never replay. The final remainder may be moved whole, retaining parent and child references. A subsequent merge may move an existing linked parent or child whole when all lineage records are visible within the reviewed cabinet and exactly match the baseline, including prior verified relocation steps. Pre-existing linked records cannot be split again in a new migration; incomplete external lineage blocks the operation. This is a staged workflow, not an atomic native transaction.

Removed leaves are **not deleted**: after empty stock record checks, they are renamed to reserved `__studio_retired_<id>` names, retaining native IDs and historical references. Studio rejects allocations/transfers into archived leaves and does not permit normal renaming or creation of reserved names. Final metadata revision can remove only the explicitly archived, empty prior leaf bindings; unrelated metadata and stock references are preserved. Physical/reference review is still required; an external InvenTree client can ignore Studio's reserved names, so keep exclusive operation window and verify actual permissions/audit locally. Retired leaf removal from the physical layout is not a native database deletion. No production authorization or catalog freeze is inferred.
